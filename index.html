Natives CSS. Volle Kontrolle.

NativeCSS ist ein Design-System, das komplett auf bereits verschiffte Browser-Features setzt - Cascade Layers, Container Queries, light-dark(), natives <dialog>, scroll-getriebene Animationen. Kein Preprocessor, kein Kompilierschritt, kein Framework-Lock-in.

Warum natives CSS

Was seit 2024/2025 in jedem aktuellen Browser steckt - und kaum genutzt wird

Die letzten Jahre haben CSS mehr echte Sprachfeatures gebracht als das letzte Jahrzehnt Tooling. NativeCSS baut ausschließlich darauf auf, statt sie hinter einem Preprocessor zu verstecken.

Cascade Layers

Reihenfolge statt Spezifitäts-Kämpfe - tokens < reset < base < helpers < components. Kein !important, keine ID-Selektoren als Notbremse.

light-dark()

EIN Wert pro Token deckt Hell und Dunkel ab - kein zweites Dark-Stylesheet, keine .dark-Klasse, die durch jede Komponente gereicht werden muss.

Container Queries

Komponenten reagieren auf ihren eigenen Platz, nicht auf den Viewport - eine Karte in der Sidebar verhält sich anders als dieselbe Karte im Hauptbereich, automatisch.

Natives HTML

<dialog> und <details> statt JS-Nachbauten für Modal/Dropdown/Off-Canvas - Fokus-Handling, ESC-Taste und ::backdrop kommen kostenlos vom Browser.

Scroll-getriebene Animationen

animation-timeline: view()/scroll() - Lesefortschritt, Scroll-Reveal, gestapelte Karten, alles ganz ohne IntersectionObserver oder Scroll-Event-Listener.

Eine Quelle der Wahrheit

Ganze Farbskalen (100-900, -on-soft) per color-mix() aus EINEM Basiswert berechnet - eine Marke in theme.css ändern, die ganze Skala zieht automatisch mit.

Cherry-Picking statt Alles-oder-nichts

Jede Komponente eine eigene, kleine Datei (components/card.css, components/modal.css, ...) - nur einbinden, was gebraucht wird. Kein Bundler, der ungenutztes CSS erst per Purge wieder herausschneiden muss.

Features im Scrollverlauf

Fünf Bausteine, die NativeCSS ausmachen

Diese Sektion ist selbst ein NativeCSS-Feature: .ncss-stack-section (components/scroll-stack.css) - Karten stapeln sich beim Scrollen, komplett ohne JavaScript, mit einem funktionierenden Fallback für Browser ohne view()-Unterstützung.

01

Design-Tokens & Theming

Eine einzige theme.css - Markenfarben, Radien, Schriften, Bewegung. Kein !important, kein zweiter Ort, an dem Werte gepflegt werden müssen.

02

Cascade Layers

Jede Datei liegt in einem benannten Layer. Reihenfolge entscheidet, nicht Spezifität - Web-Awesome-Bridge gewinnt garantiert gegen Web Awesomes eigenes Theme.

03

Scroll-getriebene Animationen

Lesefortschritt, Vollbild-Sektionen, diese Stapel-Karten hier, eine sich selbst zeichnende Roadmap-Linie - alles animation-timeline, kein JS.

04

Web Awesome nur wo nötig

Selbst gehostete Web Awesome + Font Awesome Komponenten (Rating, Tree, Popover) - niemals fürs Seitengerüst, damit die Seite nicht von ES-Modulen abhängt.

05

Barrierefreiheit eingebaut

prefers-reduced-motion global respektiert, :focus-visible-Ringe, WCAG-geprüfte Kontraste - kein nachträgliches a11y-Audit nötig.

Alle Features im Überblick

Ein solides Grundgerüst - kein Wildwuchs

Tokens & Theming

  • Fluid Typografie/Spacing (clamp())
  • Farbskalen per color-mix()
  • light-dark(), keine zweite Datei
  • Farbpaletten per [data-palette]
  • Eine theme.css für alles

Layout & Helfer

  • Grid/Stack/Cluster-Utilities
  • Container Queries statt Breakpoints
  • Responsive Tabellen (2 Strategien)
  • Elevation (Rahmen/Schatten/Radien)
  • Sticky, Scroll-Snap, Vollbild-Sektionen

Komponenten

  • Card, Modal, Off-Canvas, Dialog
  • Topbar, Nav (Mega-Menü, Dropdown, Tree)
  • Badge, Breadcrumb, Disclosure, Suche
  • Select, Slideshow, Sparkline
  • Audio/Video, Hero, Footer

Scroll & Bewegung

  • Scroll-Progress-Balken
  • Auto-Hide Topbar (wie hier oben)
  • Stacked Cards (vertikal/horizontal)
  • Sich selbst zeichnende Roadmap-Linie
  • Cross-Document View-Transitions
  • Glow/Glass/Stamped-Effekte

Web-Awesome-Integration

  • Selbst gehostet, kein CDN
  • Bridge an ncss-Tokens gekoppelt
  • Font Awesome Icons inklusive
  • Nur ergänzend, nie fürs Grundgerüst
  • Eigene lokale Referenz-Doku pro Version

Qualität

  • Kein Build-Schritt, kein node_modules
  • @supports-Fallbacks für neue CSS-Features
  • WCAG-Kontrastprüfung eingebaut
  • prefers-reduced-motion global
  • In echten Browsern getestet, nicht nur angenommen

Code-Beispiele

So sieht es in der Praxis aus

Karte + Button, automatisch dark-mode-fähig

<article class="ncss-card ncss-radius-lg ncss-border ncss-shadow-sm">
  <div class="ncss-card-body">
    <h3>Titel</h3>
    <p>Text ...</p>
    <button class="ncss-btn ncss-btn--primary">
      Aktion
    </button>
  </div>
</article>

Eigene Marke - theme.css

:root {
  --ncss-color-brand:
    light-dark(#6f6f6e, #b7b7b6);
  --ncss-color-bg:
    light-dark(#3399ff, #0b1c33);
}
/* Skalen (100-900), Badges, Buttons,
   Cards ziehen automatisch mit. */

Gestapelte Karten (wie oben)

<div class="ncss-stack-section"
     style="--ncss-stack-count: 4;">
  <div class="ncss-stack-stage">
    <article class="ncss-stack-card"
      style="--ncss-stack-index: 0">
      ...
    </article>
    <!-- ... -->
  </div>
</div>

Modal - natives <dialog>

<button command="show-modal"
        commandfor="d">Öffnen</button>
<dialog id="d" class="ncss-modal">
  <div class="ncss-modal-body">
    Kein JS-Framework nötig.
  </div>
</dialog>

Vergleich

Wie ordnet sich NativeCSS ein?

Kein Framework ist per se "falsch" - hier die ehrliche Gegenüberstellung, wofür NativeCSS eine andere Wahl trifft.

Tailwind CSS vs. NativeCSS

KriteriumTailwind CSSNativeCSS
Build-SchrittJa, PostCSS-Pipeline + Purge nötigNein - <link> reicht
AnsatzUtility-Klassen im MarkupKuratierte Komponenten + kleine Utility-Sets
ThemingConfig-Datei, eigenes Build nötigEINE theme.css, kein Build
Dark Modedark:-Präfix auf jeder Klasselight-dark(), ein Wert pro Token
Markup-LesbarkeitViele Klassen pro ElementWenige, sprechende Klassennamen
Bundle/DateigrößeAbhängig vom Purge-ErgebnisStatisches CSS, kein Purge nötig
LernkurveEigene Utility-NamenskonventionNormales CSS + Custom Properties

UIkit 3 vs. NativeCSS

KriteriumUIkit 3NativeCSS
PreprocessorLESS, Build zum Anpassen nötigKeiner - reines CSS
JS-AbhängigkeitEigenes JS für Modal/Dropdown/Off-CanvasNatives <dialog>/<details>
Theming-MechanikLESS-Variablen, neu kompilierenCSS Custom Properties, live
ResponsiveViewport-BreakpointsContainer Queries pro Komponente
Dark ModeSeparates Theme/Klasselight-dark() eingebaut
Web-Component-ErgänzungNeinWeb Awesome optional, nur wo nötig
Cascade-KontrolleSpezifität/Reihenfolge im LESSCascade Layers, explizite Reihenfolge
