Dynamische Inhalte

Die Attribut-Scripts aus dist/js/ (Count-up, Sparkline, Marquee, Downloads, Code-Block, …) suchen ihre Elemente beim Laden der Seite. Markup, das später per htmx, fetch() + innerHTML oder REDAXOs Frontend-Editing dazukommt, meldet der Host-Code mit EINEM Event - jedes Script initialisiert dann genau die neuen Elemente, nie doppelt.

Ausprobieren

Beide Buttons fügen dieselbe Karte per innerHTML ein (Count-up, Sparkline, Marquee, Code-Block). Nur der erste meldet sie danach per Event - die zweite bleibt roh, bis „Nachträglich melden“ das Event für den ganzen Bereich feuert. Mehrfaches Melden ist unschädlich.

Quelle der Demo: demo/assets/js/dynamic-content-demo.js (externe Datei, keine Inline-Scripts).

Der Vertrag

Nach dem Einfügen ein CustomEvent namens ncss-content-change am document feuern, detail.root = das neu eingefügte Element (ohne detail: das ganze Dokument wird erneut durchsucht).

document.dispatchEvent(new CustomEvent("ncss-content-change", {
  detail: { root: neuesElement }
}));
  • Idempotent: jedes Script merkt sich verarbeitete Elemente in einem eigenen WeakSet. Doppelt melden, das ganze Dokument melden, Event UND Observer - nichts wird zweimal initialisiert.
  • Bewusst kein Markierungs-Attribut: kopiertes innerHTML (htmx-Swap, REDAXO-Slice, Vorlage) brächte ein data-…-ready sonst mit - das neue Element würde fälschlich als „schon fertig“ übersprungen.
  • Cherry-pickable: jede Datei bringt ihren eigenen kleinen scan()-Helfer mit, keine gemeinsame Abhängigkeit. Wer nur count-up.js einbindet, bekommt genau das.
  • detail.root selbst wird mitgeprüft - ein eingefügtes <span data-ncss-count-up> zählt also auch, wenn es selbst die Wurzel ist. Shadow Roots (<ncss-container>) werden wie beim Laden durchsucht.

htmx

htmx:load feuert für JEDES neu eingefügte Element (detail.elt), auch bei hx-swap="outerHTML", wo das alte Ziel-Element schon aus dem DOM entfernt ist - deshalb dieses Event statt htmx:afterSwap. Beim Start feuert es einmal mit <body> - unschädlich, die Scripts sind idempotent.

// eigene Datei, z. B. assets/js/htmx-ncss.js
document.addEventListener("htmx:load", function (event) {
  document.dispatchEvent(new CustomEvent("ncss-content-change", {
    detail: { root: event.detail.elt }
  }));
});

Eigenes fetch() + innerHTML

fetch("/teaser/seite-2/")
  .then(function (response) { return response.text(); })
  .then(function (html) {
    var liste = document.querySelector("#teaser-liste");
    liste.insertAdjacentHTML("beforeend", html);
    document.dispatchEvent(new CustomEvent("ncss-content-change", {
      detail: { root: liste }
    }));
  });

Die Liste als Wurzel zu melden ist in Ordnung: bereits vorhandene Teaser sind schon verarbeitet und werden übersprungen. js/modal-router.js macht das selbst - nachgeladener Modal-Inhalt wird automatisch gemeldet.

REDAXO-Frontend-Editing

Fluid-Frontend-Editing ersetzt Slices im laufenden Dokument. Lässt sich der Editor-Code anpassen: nach dem Einsetzen eines Slices dasselbe Event mit dem Slice-Element als root feuern. Wenn nicht: content-observer.js (unten) einbinden - dann braucht der Editor gar nichts zu wissen.

Optional: content-observer.js

Für Umgebungen, deren Einfüge-Code man nicht anfassen kann. EIN MutationObserver auf dem Dokument sammelt eingefügte Elemente pro Animation-Frame und feuert pro oberstem neuen Knoten ein ncss-content-change (detail.source = "observer"). Der explizite Weg oben bleibt der empfohlene - billiger und präziser.

<script src="ncss/js/content-observer.js" defer></script>

<!-- häufig neu gerenderte Bereiche ausnehmen -->
<div data-ncss-observe="off">…</div>

Barrierefreiheit

Worauf der Host-Code achten muss

Tastatur
Die ncss-Scripts bewegen beim Initialisieren NIE den Fokus - eingefügtes Markup stiehlt ihn nicht. Fokus-Management nach einem Swap ist Sache des Host-Codes: Hat die Nutzerin das Nachladen selbst ausgelöst („Mehr laden“, Filter, Seite 2), den Fokus auf die Überschrift des neuen Bereichs setzen (tabindex="-1", nicht in der Tab-Reihenfolge) - so wie die Demo oben. Ersetzt ein Swap das gerade fokussierte Element, geht der Fokus sonst an <body> verloren. Automatische Aktualisierungen (Polling, Live-Daten) dürfen den Fokus nie bewegen.
Screenreader
Neue Inhalte knapp ansagen statt komplett vorlesen: eine kurze Meldung in einem role="status"-Element („12 weitere Treffer geladen“) oder per ncss-notify-Toast (Benachrichtigungen). aria-live direkt auf dem Swap-Container nur bei kleinen, textartigen Bereichen - bei Karten mit Marquee, Zahlen und Code wird es sonst eine lange, unübersichtliche Ansage. Count-up und Sparkline bleiben dabei korrekt: der echte Zahlentext bzw. die versteckte Wertetabelle steht von Anfang an im DOM.
Einstellungen
Nachträglich initialisierte Animationen folgen denselben Regeln wie beim Laden: unter prefers-reduced-motion: reduce zählt Count-up nicht, Reveals und Wort-Reveals bleiben statisch, Marquee und Backdrop stehen still; Forced Colors zeigt den fertigen Text. Die Abfrage läuft beim Laden des Scripts - wer die Einstellung mitten in der Sitzung umstellt, bekommt sie ab dem nächsten Seitenaufruf.
Ohne JS
Jede Komponente bleibt ohne Script bzw. ohne Event benutzbar: die Zahl steht als Text da, die Sparkline-Daten als Tabelle (sobald das Script läuft), das Laufband als statische Liste, Downloads sind normale Links. Das Event fügt nur Verhalten hinzu, nie Inhalt.

Grenzen

  • Entfernte Elemente werden nicht „abgebaut“: Listener am Element verschwinden mit ihm, einzelne document-Listener (z. B. Klick-außerhalb der Live-Suche, visibilitychange beim Backdrop) bleiben bis zum Seitenwechsel bestehen. Backdrop-Timer, Hide-on-Scroll und Stack-Fallback räumen entfernte Elemente selbst aus.
  • Ein Element, das ein Script bereits umgebaut hat (Marquee-Kopie, Sparkline-Tabelle, Copy-Button, Wort-Spans), darf als Kopie wieder eingefügt werden - die Scripts erkennen das und bauen nicht doppelt. Ein Combobox-Enhancement wird dagegen nicht neu verdrahtet, wenn sein Ersatz-Markup mitkopiert wurde (data-ncss-combobox bleibt bewusst ein Attribut) - das native Element vor dem Enhancement ausliefern.
  • Verschieben statt Neu-Einfügen (Slice umsortieren, hx-preserve): Custom Elements hängen ihre document-Listener beim erneuten Verbinden wieder an (<ncss-command-palette>, <ncss-hovercard> geprüft). Attribut-Scripts behalten ihren Zustand am Element, ein verschobenes Element braucht kein Event.
