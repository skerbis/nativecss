Testen

ncss nimmt dir viel ab, aber nur ein Test deiner fertigen Seite zeigt, ob Inhalt, Reihenfolge und Beschriftungen stimmen. Automatische Werkzeuge finden nur einen Teil der Probleme - der Rest braucht Tastatur, Screenreader und ein paar Minuten Aufmerksamkeit.

Automatische Prüfung

Automatische Tests sind schnell und finden zuverlässig typische technische Fehler: fehlende alt-Attribute, Felder ohne Label, zu geringen Farbkontrast, doppelte IDs, falsche ARIA-Attribute. Ob ein Alternativtext sinnvoll oder eine Fehlermeldung verständlich ist, können sie nicht beurteilen.

  • axe DevTools (Browser-Erweiterung für Chrome, Edge, Firefox) - prüft die aktuelle Seite inklusive dynamisch geöffneter Zustände. Öffne Menüs, Dialoge und Off-Canvas vor dem Scan, sonst werden sie nicht geprüft.
  • Lighthouse (in den Chrome-Entwicklerwerkzeugen unter "Lighthouse", Kategorie "Barrierefreiheit") - baut auf axe auf und liefert einen Punktwert. 100 Punkte bedeuten nur: keine automatisch erkennbaren Fehler.
  • Lighthouse auf der Kommandozeile - für mehrere Seiten oder regelmäßige Prüfungen:
npx lighthouse https://example.org/ --only-categories=accessibility --view

# Ergebnis als JSON speichern, z. B. für einen Vergleich
npx lighthouse https://example.org/kontakt/ --only-categories=accessibility --output=json --output-path=./a11y-kontakt.json
  • Für lokale Seiten zuerst einen lokalen Server starten (z. B. npx serve) und dessen Adresse prüfen.
  • Jeden Seitentyp einmal prüfen (Startseite, Inhaltsseite, Formular, Liste), nicht nur die Startseite.
  • In hellem und dunklem Modus prüfen - Kontraste können in einem Modus passen und im anderen nicht, vor allem bei eigenen Farben.

Tastatur-Check

Maus zur Seite legen und die Seite nur mit Tab, Umschalt+Tab, Enter, Leertaste, Pfeiltasten und Esc bedienen. In Safari vorher unter Einstellungen → Erweitert die Option einschalten, mit der Tabulatortaste alle Objekte einer Webseite zu markieren - sonst springt Tab nicht zu Links.

  • Der erste Tab zeigt den Skip-Link ("Zum Inhalt springen"), Enter springt in den Hauptinhalt.
  • Jedes interaktive Element ist erreichbar - Links, Buttons, Felder, Menüs, Player, Karten mit Link.
  • Der Fokus ist immer sichtbar (ncss: Rahmen per :focus-visible) und nie von einer festen Kopfleiste, einem Cookie-Banner oder einem Toast verdeckt.
  • Die Reihenfolge folgt dem Lesefluss - kein Springen kreuz und quer durch das Layout.
  • Dialoge, Off-Canvas und Menüs lassen sich mit Esc schließen; der Fokus kehrt danach zum auslösenden Button zurück.
  • Nirgends bleibt der Fokus hängen (Tastaturfalle) - auch nicht in eingebetteten Karten, Videos oder iframes.
  • Nichts passiert ungefragt beim Fokussieren oder Auswählen: kein automatisches Absenden beim Wechseln einer Auswahl, kein Seitenwechsel beim Fokus.

Screenreader-Schnelltest

Ein kurzer Durchgang mit einem Screenreader zeigt, ob Struktur und Beschriftungen ankommen. Du musst dafür kein Profi sein - es reicht, die Überschriften- und Landmarken-Navigation zu nutzen und die Formulare einmal auszufüllen.

  • Der Seitentitel wird beim Laden angesagt und beschreibt die Seite.
  • Die Überschriftenliste ergibt ein sinnvolles Inhaltsverzeichnis - genau eine h1, keine übersprungenen Ebenen.
  • Landmarken sind vorhanden: Kopf (header), Navigation (nav mit Namen, wenn es mehrere gibt), Hauptinhalt (main), Fuß (footer).
  • Buttons und Links haben verständliche Namen - auch Icon-Buttons. Kein "Button", "Link" oder "Mehr" ohne Zusammenhang.
  • Formularfelder sagen Label, Pflicht-Status, Hinweis und Fehler an.
  • Statusmeldungen (Treffer der Live-Suche, Toasts, Player-Zustand) werden angesagt, ohne dass der Fokus springt.
  • Listen, die als Listen gestylt sind (.ncss-list--dot), werden als Liste mit Anzahl angesagt - dafür braucht das Markup role="list".

Zoom und Reflow prüfen

  • Browserfenster auf 1280 px Breite, Zoom auf 200 %: alles lesbar und bedienbar, nichts überlappt oder ist abgeschnitten.
  • Zoom auf 400 % (entspricht 320 CSS-Pixeln): eine Spalte, kein seitliches Scrollen der Seite - Tabellen und Code dürfen in ihrem eigenen Rahmen scrollen.
  • Alternativ: Gerätemodus der Entwicklerwerkzeuge auf 320 px Breite stellen.
  • Nur-Text-Zoom in Firefox (Ansicht → Zoom → Nur Text zoomen) auf 200 %: Schrift wächst, Boxen wachsen mit.
  • Textabstände per CSS-Snippet oder Bookmarklet erhöhen: kein Text verschwindet.
  • Festsitzende Kopfleisten und Cookie-Banner nehmen bei 200 % nicht den halben Bildschirm ein.

Kontrastmodus (forced colors)

Windows-Kontrastdesigns ersetzen alle Farben der Seite durch wenige Systemfarben. Hintergrundbilder, Schatten und Hintergrundfarben verschwinden dabei. Was nur über Farbe oder Schatten erkennbar war, ist dann unsichtbar.

  • Windows: Einstellungen → Barrierefreiheit → Kontrastdesigns, ein Design wählen (Tastenkürzel: linke Alt+linke Umschalt+Druck).
  • Chrome/Edge-Entwicklerwerkzeuge: Befehlsmenü (Strg/⌘+Umschalt+P) → "Show Rendering" → "Emulate CSS media feature forced-colors" auf active.
  • Prüfen: Buttons und Felder haben sichtbare Umrisse, der Fokusrahmen ist sichtbar, Icons sind erkennbar (SVG mit currentColor), Zustände wie "ausgewählt" oder "aktiv" sind nicht nur farblich markiert.
  • Hintergrundvideos (js/video-bg.js) laden in diesem Modus bewusst nicht, es bleibt das Poster.

Reduzierte Bewegung und Farbschema

  • Emulation: Chrome/Edge-Entwicklerwerkzeuge, Befehlsmenü → "Show Rendering" → "Emulate CSS media feature prefers-reduced-motion" auf reduce; im selben Bereich prefers-color-scheme für hell/dunkel.
  • System: macOS Einstellungen → Bedienungshilfen → Anzeige → "Bewegung reduzieren"; iOS Einstellungen → Bedienungshilfen → Bewegung; Windows Einstellungen → Barrierefreiheit → Visuelle Effekte → "Animationseffekte" aus.
  • Prüfen: keine Parallax- oder Scroll-Animationen, Laufbänder stehen, Hintergrundvideos zeigen nur das Poster, sanftes Scrollen ist aus. Inhalt bleibt trotzdem vollständig sichtbar - nichts darf erst durch eine Animation erscheinen.
  • Eigene JavaScript-Animationen prüfen: CSS-Regeln aus reset.css erreichen sie nicht.

Code prüfen mit dem Inspektor dieser Website

Auf jeder Seite dieser Website gibt es unten rechts den Schalter Inspect (Alt+I, Mac ⌥+I). Damit klickst du ein Element an und siehst das bereinigte HTML, die Erklärung jeder ncss-Klasse und die zugehörige Datei. Praktisch, um zu prüfen, wie ein Beispiel ARIA-Attribute, Labels und role="list" setzt, bevor du es übernimmst.

Für deine eigene Seite übernimmt diese Aufgabe der Barrierefreiheitsbaum der Browser-Entwicklerwerkzeuge (Chrome/Edge: Elemente → "Barrierefreiheit", Firefox: Tab "Barrierefreiheit"). Er zeigt Rolle, Name und Zustand jedes Elements so, wie Screenreader sie bekommen. Mehr zum Inspektor: Code-Inspektor.

Ein sinnvoller Ablauf

  • Bei jeder neuen Komponente oder Vorlage: Tastatur-Check und axe-Scan - das dauert wenige Minuten.
  • Vor einem Release: Lighthouse über alle Seitentypen, Zoom- und Kontrastmodus-Check, ein Screenreader-Durchgang durch die wichtigsten Abläufe (Navigation, Suche, Formular).
  • Gefundene Probleme festhalten und, solange sie offen sind, in der Barrierefreiheitserklärung nennen.
  • Wo möglich mit Menschen testen, die selbst assistive Technik nutzen. Kein Werkzeug ersetzt ihre Erfahrung.
