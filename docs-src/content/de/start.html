CSS, das der Browser schon kann.

NativeCSS ist ein Designsystem aus reinem, modernem CSS: Cascade Layers, Container Queries, light-dark() und native HTML-Elemente statt Preprocessor, Bundler und JavaScript-Nachbauten - barrierefrei von Grund auf. Alles mit zwei Zeilen einbinden - oder nur die Bausteine, die du brauchst.

Handbuch öffnen Beispiele ansehen GitHub

Alles oder nur, was du brauchst

Kein Kompilieren, kein Purgen: die Dateien sind fertiges CSS, das der Browser direkt lädt. ncss.css bringt alles mit - oder du nimmst per Cherry-Picking nur die Komponenten, die deine Seite wirklich nutzt. Jede ist eine eigene kleine Datei.

Zum Vergleich - so sieht eine übliche Build-Kette aus: 
npm install -D sass postcss autoprefixer
npm install -D vite tailwindcss
npx tailwindcss init
# vite.config.js, postcss.config.js, purge …
npm run build

Vier Browser-Features tragen alles

Jede Komponente baut auf denselben vier Plattform-Bausteinen auf - hier live, direkt zum Ausprobieren.

Cascade Layers

Reihenfolge statt Spezifität: eigenes CSS ohne Layer gewinnt immer - ganz ohne !important.

@layer tokens, reset, base, helpers, components;
button { background: #b4400f; } /* ohne Layer: gewinnt */

Barrierefrei von Grund auf

Barrierefreiheit ist kein Zusatz-Modul, sondern in jedem Baustein eingebaut - als Grundlage für Websites nach WCAG 2.2 AA.

  • Native, semantische Elemente - <dialog>, <details>, echte Buttons und Links statt nachgebauter Widgets.
  • Sichtbarer Fokus überall und Tastatur-Muster nach dem WAI-ARIA Authoring Practices Guide.
  • Kontrastsichere Tokens mit light-dark() - Hell und Dunkel aus einer Quelle.
  • Nutzer-Einstellungen respektiert: reduzierte Bewegung, mehr Kontrast, weniger Transparenz, Forced Colors.
  • 200 % Zoom und Reflow dank fließender Größen und Container Queries.
  • Funktioniert ohne JavaScript - Skripte verbessern nur, sie tragen nichts.

Seit dem 28. Juni 2025 gilt in Deutschland das Barrierefreiheitsstärkungsgesetz (BFSG) für viele digitale Produkte und Dienstleistungen. NativeCSS hilft, barrierefreie Websites zu bauen - konform wird eine Website aber erst durch ihren Inhalt und ihre Umsetzung; NativeCSS allein kann das nicht garantieren. Ganze Websites, nur aus NativeCSS

Eine Gemeinde, ein Hotel, ein Verwaltungs-Backend und mehr - jedes Beispiel mit eigenem Design.

Wann NativeCSS - und wann nicht

Ehrlich eingeordnet, damit die Entscheidung schnell fällt.

Passt gut

  • Websites und CMS-Themes (z.B. REDAXO, WordPress), die ohne Build-Pipeline auskommen sollen.
  • Projekte, die aktuelle Browser voraussetzen dürfen (Evergreen: Chrome, Edge, Firefox, Safari).
  • Teams, die lieber natives CSS lesen als Utility-Klassen oder Sass-Mixins.
  • Barrierefreiheit von Anfang an: Fokus, Kontraste, reduzierte Bewegung.

Eher nicht

  • Wenn sehr alte Browser (z.B. Internet Explorer, Safari < 16) voll unterstützt werden müssen.
  • Wenn das Projekt bereits fest auf ein Utility-First-Framework mit eigener Toolchain setzt.
  • Für komplexe App-Widgets ohne natives Gegenstück - dort Web Awesome über die Bridge nutzen.

Details: Bekannte Grenzen.
