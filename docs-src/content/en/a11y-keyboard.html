Keyboard

Everything you can do with a mouse must also work with a keyboard (WCAG 2.1.1) - and it must always be clear where focus currently is (WCAG 2.4.7).

Principles

  • Focus is always visible - reset.css only removes the focus ring for mouse/touch (:focus) and gives :focus-visible a consistent ring in --ncss-color-focus-ring with a 2 px offset. Components never gate :focus-visible behind (hover: hover). In your own components: never remove the ring without a replacement.
  • Logical order - tab order follows the DOM. Rearranging layout with order, flex-direction: row-reverse or grid placement only changes what you see, not the order - the source order itself has to make sense. No positive tabindex.
  • No keyboard traps (WCAG 2.1.2) - the only intended exception is modal dialogs (.ncss-modal, .ncss-offcanvas, the mobile nav panel, lightbox, command palette): opened via showModal(), the rest of the page becomes inert, Esc closes, and focus returns to the trigger.
  • Skip link - .ncss-skip-link as the first element after <body>, targeting <main> with id="main" (see Principles). This website uses one on every page - press Tab once after loading.
  • Native controls - <button> instead of a clickable <div>, <a href> for navigation, <details> for disclosures. Then Enter/Space just work.
  • Make scroll containers reachable - a wide table in .ncss-table-scroll gets role="region", aria-label and tabindex="0" in the markup so it can be focused and scrolled with the keyboard (WCAG 1.4.10). The same is recommended for a .ncss-slideshow-track.
<div class="ncss-table-scroll" role="region" aria-label="Price comparison" tabindex="0">
  <table>...</table>
</div>

Try It Yourself

Click next to the example, then move forward and back with Tab and Shift+Tab. Enter or Space expands the disclosure and opens the dialog. Inside the dialog, focus stays contained; Esc or the close button ends it - afterwards focus is back on the button that opened it.

What happens when it expands?

The native <details> responds to Enter and Space, and screen readers announce "expanded"/"collapsed" - with no script and no ARIA.

<button type="button" class="ncss-btn ncss-btn--primary"
        command="show-modal" commandfor="dialog1">Open dialog</button>

<dialog id="dialog1" class="ncss-modal" aria-labelledby="dialog1-title">
  <button type="button" class="ncss-dialog-close" command="close"
          commandfor="dialog1" aria-label="Close">&times;</button>
  <div class="ncss-modal-header"><h3 id="dialog1-title">Modal dialog</h3></div>
  <div class="ncss-modal-body">...</div>
</dialog>

command/commandfor works without any script in current browsers - for older ones, js/command-fallback.js fills in exactly show-modal and close.

Your Own Components

  • First check whether a native element fits (<details>, <dialog>, a radio group, popover) - then the keyboard part is already solved.
  • If you build a widget yourself, follow the matching pattern in the WAI-ARIA Authoring Practices Guide - key bindings and roles go together.
  • Single-character shortcuts (like K in the player) only while the element has focus, or make them switchable (WCAG 2.1.4). That's why the command palette's global shortcuts are opt-in attributes.
  • After closing an overlay, return focus somewhere sensible - usually the trigger.
  • Focused elements must not disappear under sticky headers (WCAG 2.4.11) - set scroll-padding-top to match the bar's height.
