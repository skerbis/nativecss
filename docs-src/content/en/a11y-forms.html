Forms & Error Messages

Forms are where barriers cost the most: if you cannot understand a field or find an error, you are stuck. ncss provides the look (helpers/forms.css) - labels, associations and error messages come from your markup.

Every field needs a label

Every input needs a visible, persistent name in a <label> that is linked to the field via for/id (or wraps it). Clicking the label then focuses the field, screen readers announce the name, and voice control users can target the field by its visible text (WCAG 2.5.3 "Label in Name").

  • placeholder is not a label. It disappears as soon as you type, often has too little contrast and is not announced as the field name by every tool. At most it is good for an example format ("e.g. 12345").
  • If a visible label really does not fit the design (a search field with a magnifier button), hide it with .ncss-visually-hidden - do not leave it out.
  • Label buttons with what they do: "Send registration" rather than "OK". An icon button needs aria-label or hidden text.
<div class="ncss-field">
  <label class="ncss-label" for="city">City</label>
  <input class="ncss-input" id="city" name="city" autocomplete="address-level2">
</div>

Marking required fields

.ncss-label--required adds a red * to the label via ::after. That is only the visual part - you need to add two things yourself:

  • The required attribute on the field. Only then do screen readers announce "required" and the browser check the field on submit.
  • An explanation of the asterisk before the form ("Fields marked * are required"). The symbol alone is not self-explanatory for everyone, and some screen readers read it out as "star".
<p>Fields marked * are required.</p>
<div class="ncss-field">
  <label class="ncss-label ncss-label--required" for="email">Email</label>
  <input class="ncss-input" id="email" name="email" type="email" required autocomplete="email">
</div>

Linking hints and errors with aria-describedby

Hint text (.ncss-field-hint) and error text (.ncss-field-error) are shown below the field. So they are also read out when the field receives focus, link them with aria-describedby - several IDs separated by spaces. The order of the IDs is the reading order.

  • Hints that matter before typing (format, length) belong above or directly below the field - not only in the error message (WCAG 3.3.2).
  • Error messages name the problem and, where possible, the fix: "Enter an email address that includes an @" rather than "Invalid input" (WCAG 3.3.1, 3.3.3).
  • Do not signal errors by colour alone: the red border from :user-invalid is an addition, the meaning is carried by the text (WCAG 1.4.1).
<div class="ncss-field">
  <label class="ncss-label ncss-label--required" for="zip">ZIP code</label>
  <input class="ncss-input" id="zip" name="zip" required
         inputmode="numeric" pattern="[0-9]{5}" autocomplete="postal-code"
         aria-describedby="zip-hint">
  <p class="ncss-field-hint" id="zip-hint">5 digits, e.g. 90210</p>
</div>

Error state: :user-invalid and aria-invalid

.ncss-input, .ncss-select and .ncss-textarea get a red border on :user-invalid. :user-invalid only applies after someone has interacted with the field or tried to submit the form - so an empty required field is not already "wrong" when the page loads. It works without JavaScript and is driven by the native attributes (required, type="email", pattern, min/max, minlength).

On submit, the browser shows its own error bubble at the first invalid field and moves focus there. For many forms that is enough. If your server validates as well (and it always should), it re-renders the page with errors. Then:

  • Set aria-invalid="true" on the invalid field - screen readers announce "invalid".
  • Put the error text in a .ncss-field-error with its own ID below the field and add it to aria-describedby.
  • Keep what the person has already typed - nobody should have to enter everything again (WCAG 3.3.7 "Redundant Entry").

Important: ncss only colours :user-invalid, not [aria-invalid="true"]. For server-side errors, add the rule yourself (this page does that for the example below):

.ncss-input[aria-invalid="true"],
.ncss-select[aria-invalid="true"],
.ncss-textarea[aria-invalid="true"] {
  border-color: var(--ncss-color-danger);
}
<div class="ncss-field">
  <label class="ncss-label ncss-label--required" for="email">Email</label>
  <input class="ncss-input" id="email" name="email" type="email" required
         autocomplete="email" value="anna.example.com"
         aria-invalid="true" aria-describedby="email-error">
  <p class="ncss-field-error" id="email-error">Enter an email address that includes an @, e.g. anna@example.com</p>
</div>

Groups: fieldset and legend

Related fields - especially radio buttons and checkbox groups - go into a <fieldset> with a <legend>. The legend is the question, the labels are the answers. Screen readers announce the legend when entering the group. ncss styles fieldset/legend without a class.

<fieldset>
  <legend>How would you like us to contact you?</legend>
  <label class="ncss-choice"><input type="radio" name="contact" value="email" checked> Email</label>
  <label class="ncss-choice"><input type="radio" name="contact" value="phone"> Phone</label>
</fieldset>

For a toggle (.ncss-switch) add role="switch" - it is then announced as a switch instead of a checkbox.

Input group: label before it, not inside

With .ncss-input-group (field and button merged) the label is a sibling before the group, never a child inside it - otherwise it would count as :first-child and receive the corner rounding. For several merged fields without room for their own label (first name/last name) give each field an aria-label. Details: Forms - Input group.

<label class="ncss-label" for="search">Search term</label>
<div class="ncss-input-group">
  <input class="ncss-input" type="search" id="search" name="q">
  <button type="submit" class="ncss-btn ncss-btn--primary">Search</button>
</div>

autocomplete: state the purpose of a field

Fields that ask for information about the person filling in the form need the matching autocomplete value (WCAG 1.3.5). The browser can then fill them in - a big help for people with motor or cognitive disabilities, and fewer typos for everyone.

Error summary after submitting

For longer forms, a summary of all errors above the form helps. The pattern:

  • A heading that names the problem ("There are 2 problems with your answers"), followed by a list with one link per error. Each link points to its field via href="#field-id".
  • After the reload, move focus to the summary (tabindex="-1" plus autofocus or a small script) - keyboard and screen reader users land right there.
  • Prefix the page title: <title>Error: Registration - Example</title>. The title is the first thing announced on load.
  • A link to #field-id scrolls to the field and moves the tab starting point there, but does not focus the field in every browser. If you want that, focus it with a script.

The example shows the state "after submitting"; focus is deliberately not moved automatically so this handbook page does not jump on load.

  • Enter an email address that includes an @

Complete example form

Everything together, without JavaScript: visible labels, an explained asterisk, required, linked hints, autocomplete, a radio group in a fieldset. Click "Send request" without filling anything in: the browser reports the first missing field and the fields get their red border via :user-invalid. The example uses method="dialog" so submitting sends nothing and does not reload the page - in your project you would use method="post" and an action.
