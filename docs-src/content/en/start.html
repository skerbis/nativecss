CSS the browser already knows.

NativeCSS is a design system made of plain, modern CSS: cascade layers, container queries, light-dark() and native HTML elements instead of a preprocessor, a bundler and JavaScript re-implementations - accessible from the ground up. Add two lines - done.

Open the docs See examples GitHub

Two lines instead of a build chain

No compiling, no purging: the files are finished CSS the browser loads directly - three equal ways to include them.

For comparison - a typical build chain: 
npm install -D sass postcss autoprefixer
npm install -D vite tailwindcss
npx tailwindcss init
# vite.config.js, postcss.config.js, purge …
npm run build

Four browser features carry everything

Every component is built on the same four platform features - live here, to try out right away.

Cascade Layers

Order instead of specificity: your own unlayered CSS always wins - no !important.

@layer tokens, reset, base, helpers, components;
button { background: #b4400f; } /* unlayered: wins */

Accessible from the ground up

Accessibility is not an add-on module but built into every building block - a foundation for websites targeting WCAG 2.2 AA.

  • Native, semantic elements - <dialog>, <details>, real buttons and links instead of re-built widgets.
  • Visible focus everywhere and keyboard patterns following the WAI-ARIA Authoring Practices Guide.
  • Contrast-safe tokens with light-dark() - light and dark from one source.
  • User preferences respected: reduced motion, more contrast, reduced transparency, forced colors.
  • 200 % zoom and reflow thanks to fluid sizes and container queries.
  • Works without JavaScript - scripts only enhance, they carry nothing.

Since 28 June 2025 the German Accessibility Strengthening Act (BFSG, implementing the European Accessibility Act) applies to many digital products and services. NativeCSS helps you build accessible websites - but a site becomes compliant through its content and implementation; NativeCSS alone cannot guarantee that. More in the accessibility docs.

When NativeCSS - and when not

An honest take, so the decision is quick.

Good fit

  • Websites and CMS themes (e.g. REDAXO, WordPress) that should work without a build pipeline.
  • Projects that may require current browsers (evergreen: Chrome, Edge, Firefox, Safari).
  • Teams who prefer reading native CSS over utility classes or Sass mixins.
  • Accessibility from the start: focus, contrast, reduced motion.

Rather not

  • When very old browsers (e.g. Internet Explorer, Safari < 16) must be fully supported.
  • When the project is already committed to a utility-first framework with its own toolchain.
  • For complex app widgets without a native counterpart - use Web Awesome via the bridge there.

Details: Known limitations.
