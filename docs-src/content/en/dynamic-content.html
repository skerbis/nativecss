Dynamic content

The attribute-based scripts in dist/js/ (count-up, sparkline, marquee, downloads, code block, …) look for their elements when the page loads. Markup added later by htmx, fetch() + innerHTML or REDAXO's frontend editing is announced by the host code with ONE event - every script then initialises exactly the new elements, never twice.

Try it

Both buttons insert the same card via innerHTML (count-up, sparkline, marquee, code block). Only the first announces it afterwards - the second stays raw until “Announce afterwards” fires the event for the whole area. Announcing repeatedly is harmless.

Demo source: demo/assets/js/dynamic-content-demo.js (external file, no inline scripts).

The contract

After inserting, fire a CustomEvent named ncss-content-change on document, with detail.root = the newly inserted element (without detail, the whole document is scanned again).

document.dispatchEvent(new CustomEvent("ncss-content-change", {
  detail: { root: newElement }
}));
  • Idempotent: each script remembers processed elements in its own WeakSet. Announce twice, announce the whole document, use the event AND the observer - nothing is initialised twice.
  • Deliberately no marker attribute: copied innerHTML (htmx swap, REDAXO slice, template) would otherwise carry a data-…-ready along and the new element would wrongly be skipped as “already done”.
  • Cherry-pickable: every file ships its own tiny scan() helper, no shared dependency. Include only count-up.js and that is exactly what you get.
  • detail.root itself is checked too - an inserted <span data-ncss-count-up> counts even when it is the root. Shadow roots (<ncss-container>) are searched just like on load.

htmx

htmx:load fires for EVERY newly added element (detail.elt), also with hx-swap="outerHTML", where the old target is already gone from the DOM - hence this event rather than htmx:afterSwap. It fires once with <body> on start-up - harmless, the scripts are idempotent.

// own file, e.g. assets/js/htmx-ncss.js
document.addEventListener("htmx:load", function (event) {
  document.dispatchEvent(new CustomEvent("ncss-content-change", {
    detail: { root: event.detail.elt }
  }));
});

Your own fetch() + innerHTML

fetch("/teasers/page-2/")
  .then(function (response) { return response.text(); })
  .then(function (html) {
    var list = document.querySelector("#teaser-list");
    list.insertAdjacentHTML("beforeend", html);
    document.dispatchEvent(new CustomEvent("ncss-content-change", {
      detail: { root: list }
    }));
  });

Announcing the whole list is fine: existing teasers are already processed and get skipped. js/modal-router.js does this itself - content loaded into the modal is announced automatically.

REDAXO frontend editing

Fluid frontend editing replaces slices in the live document. If you can adapt the editor code: fire the same event with the slice element as root after inserting it. If not: include content-observer.js (below) - then the editor doesn't need to know anything.

Optional: content-observer.js

For environments whose insertion code you cannot touch. ONE MutationObserver on the document collects inserted elements per animation frame and fires one ncss-content-change per topmost new node (detail.source = "observer"). The explicit path above remains the recommended one - cheaper and more precise.

<script src="ncss/js/content-observer.js" defer></script>

<!-- exclude areas that re-render often -->
<div data-ncss-observe="off">…</div>

Accessibility

What the host code has to take care of

Keyboard
The ncss scripts NEVER move focus while initialising - inserted markup does not steal it. Focus management after a swap is the host code's job: if the user triggered the load themselves (“Load more”, filters, page 2), move focus to the heading of the new region (tabindex="-1", not in the tab order) - like the demo above. If a swap replaces the focused element, focus is otherwise lost to <body>. Automatic updates (polling, live data) must never move focus.
Screen readers
Announce new content briefly instead of reading all of it: a short message in a role="status" element (“12 more results loaded”) or an ncss-notify toast (notifications). Put aria-live directly on the swap container only for small, text-like areas - with cards containing a marquee, numbers and code it becomes a long, confusing announcement. Count-up and sparkline stay correct: the real number text and the hidden value table are in the DOM from the start.
Settings
Animations initialised later follow the same rules as on load: with prefers-reduced-motion: reduce count-up does not count, reveals and word reveals stay static, marquee and backdrop stand still; forced colors shows the final text. The preference is read when the script loads - a change mid-session applies from the next page view.
Without JS
Every component stays usable without the script or without the event: the number is plain text, the sparkline data a table (once the script runs), the marquee a static list, downloads are normal links. The event only adds behaviour, never content.

Limits

  • Removed elements are not “torn down”: listeners on the element go with it, a few document listeners (e.g. click-outside of the live search, visibilitychange of the backdrop) stay until the next page load. Backdrop timers, hide-on-scroll and the stack fallback drop removed elements themselves.
  • An element a script has already rebuilt (marquee copy, sparkline table, copy button, word spans) may be inserted again as a copy - the scripts detect it and don't build twice. A combobox enhancement is not rewired when its replacement markup was copied along (data-ncss-combobox stays an attribute on purpose) - deliver the native element from before the enhancement.
  • Moving instead of re-inserting (reordering slices, hx-preserve): custom elements re-attach their document listeners when reconnected (<ncss-command-palette>, <ncss-hovercard> verified). Attribute scripts keep their state on the element, a moved element needs no event.
