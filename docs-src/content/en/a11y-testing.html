Testing

ncss takes a lot off your plate, but only testing your finished page shows whether content, order and labels are right. Automated tools only find some of the problems - the rest needs a keyboard, a screen reader and a few minutes of attention.

Automated checks

Automated tests are fast and reliably catch typical technical errors: missing alt attributes, fields without labels, insufficient colour contrast, duplicate IDs, invalid ARIA attributes. They cannot judge whether an alt text makes sense or an error message is understandable.

  • axe DevTools (browser extension for Chrome, Edge, Firefox) - checks the current page including dynamically opened states. Open menus, dialogs and off-canvas panels before scanning, otherwise they are not checked.
  • Lighthouse (in Chrome DevTools under "Lighthouse", category "Accessibility") - built on axe and gives you a score. 100 points only means: no automatically detectable errors.
  • Lighthouse on the command line - for several pages or regular checks:
npx lighthouse https://example.org/ --only-categories=accessibility --view

# Save the result as JSON, e.g. to compare runs
npx lighthouse https://example.org/contact/ --only-categories=accessibility --output=json --output-path=./a11y-contact.json
  • For local pages, start a local server first (e.g. npx serve) and test its address.
  • Check every page type once (home page, content page, form, listing), not just the home page.
  • Check in light and dark mode - contrast can pass in one mode and fail in the other, especially with your own colours.

Keyboard check

Put the mouse aside and use the page with Tab, Shift+Tab, Enter, Space, arrow keys and Esc only. In Safari, first turn on the option under Settings → Advanced that lets the Tab key highlight every item on a webpage - otherwise Tab skips links.

  • The first Tab reveals the skip link ("Skip to content"), Enter jumps to the main content.
  • Every interactive element can be reached - links, buttons, fields, menus, players, cards with a link.
  • Focus is always visible (ncss: outline via :focus-visible) and never hidden behind a sticky header, a cookie banner or a toast.
  • The order follows the reading flow - no jumping back and forth across the layout.
  • Dialogs, off-canvas panels and menus close with Esc; focus then returns to the button that opened them.
  • Focus never gets stuck (keyboard trap) - not in embedded maps, videos or iframes either.
  • Nothing happens unexpectedly on focus or selection: no automatic submit when a selection changes, no page change on focus.

Which keys the ncss components support: Keyboard.

Screen reader quick check

A short pass with a screen reader shows whether structure and labels come across. You do not need to be an expert - navigating by headings and landmarks and filling in the forms once is enough.

Screen readerStartUseful commands
VoiceOver (macOS, with Safari)⌘+F5Ctrl+⌥+U opens the rotor (headings, links, landmarks, form controls), Ctrl+⌥+→ reads on
VoiceOver (iOS, iPadOS)Settings → Accessibility → VoiceOver, or - if set up as the accessibility shortcut - triple-click the side buttonSwipe right/left: next/previous item, double-tap: activate, two-finger rotate: rotor
NVDA (Windows, free, with Firefox or Chrome)Ctrl+Alt+N after installingH headings, D landmarks, K links, F form fields, NVDA+F7 elements list
TalkBack (Android, with Chrome)Settings → Accessibility → TalkBack, or - if set up as the shortcut - hold both volume keysSwipe right/left: next/previous item, double-tap: activate
  • The page title is announced on load and describes the page.
  • The list of headings reads like a sensible table of contents - exactly one h1, no skipped levels.
  • Landmarks are present: header (header), navigation (nav, named if there is more than one), main content (main), footer (footer).
  • Buttons and links have understandable names - icon buttons too. No "button", "link" or "more" without context.
  • Form fields announce label, required state, hint and error.
  • Status messages (live search results, toasts, player state) are announced without focus moving.
  • Lists styled as lists (.ncss-list--dot) are announced as a list with a count - that needs role="list" in the markup.

Checking zoom and reflow

  • Browser window 1280 px wide, zoom to 200%: everything readable and usable, nothing overlaps or is clipped.
  • Zoom to 400% (equivalent to 320 CSS pixels): one column, no sideways scrolling of the page - tables and code may scroll inside their own frame.
  • Alternatively: set the DevTools device mode to 320 px width.
  • Text-only zoom in Firefox (View → Zoom → Zoom Text Only) to 200%: text grows, boxes grow with it.
  • Increase text spacing with a CSS snippet or bookmarklet: no text disappears.
  • Sticky headers and cookie banners do not take up half the screen at 200%.

The values and the CSS snippet for checking text spacing: Zoom, Reflow & Text Spacing.

Contrast themes (forced colors)

Windows contrast themes replace every colour on the page with a handful of system colours. Background images, shadows and background colours disappear. Anything that was only recognisable by colour or shadow becomes invisible.

  • Windows: Settings → Accessibility → Contrast themes, pick a theme (shortcut: left Alt+left Shift+Print Screen).
  • Chrome/Edge DevTools: Command menu (Ctrl/⌘+Shift+P) → "Show Rendering" → set "Emulate CSS media feature forced-colors" to active.
  • Check: buttons and fields have visible outlines, the focus outline is visible, icons are recognisable (SVG with currentColor), states like "selected" or "active" are not marked by colour alone.
  • Background videos (js/video-bg.js) deliberately do not load in this mode; the poster remains.

Reduced motion and colour scheme

  • Emulation: Chrome/Edge DevTools, command menu → "Show Rendering" → set "Emulate CSS media feature prefers-reduced-motion" to reduce; prefers-color-scheme for light/dark is in the same panel.
  • System: macOS System Settings → Accessibility → Display → "Reduce motion"; iOS Settings → Accessibility → Motion; Windows Settings → Accessibility → Visual effects → turn off "Animation effects".
  • Check: no parallax or scroll animations, marquees stand still, background videos only show the poster, smooth scrolling is off. Content still has to be fully visible - nothing may depend on an animation to appear.
  • Check your own JavaScript animations: the CSS rules in reset.css do not reach them.

Which settings ncss responds to: User Preferences.

Checking code with this website's inspector

Every page of this website has an Inspect toggle at the bottom right (Alt+I, Mac ⌥+I). Turn it on, click an element and you see the cleaned-up HTML, an explanation of every ncss class and the file it comes from. Handy for checking how an example sets ARIA attributes, labels and role="list" before you copy it.

For your own page, the accessibility tree in the browser DevTools does this job (Chrome/Edge: Elements → "Accessibility", Firefox: "Accessibility" tab). It shows the role, name and state of each element exactly as screen readers receive them. More about the inspector: Code Inspector.

A sensible routine

  • For every new component or template: a keyboard check and an axe scan - it takes a few minutes.
  • Before a release: Lighthouse across all page types, a zoom and contrast theme check, a screen reader pass through the key journeys (navigation, search, forms).
  • Record the problems you find and, while they remain open, list them in the accessibility statement.
  • Where possible, test with people who use assistive technology themselves. No tool replaces their experience.
