NativeCSS Handbuch

Referenz für das ncss-Design-System: Prinzipien, Architektur, Tokens und wie man es erweitert, ohne die Grundprinzipien zu brechen.

Prinzipien

  • Native zuerst. Cascade Layers statt Spezifitäts-Kämpfe, Container Queries statt Viewport-Breakpoints, light-dark() statt zweitem Dark-Stylesheet, native <dialog>/<details> statt JS-Nachbauten. Web Awesome ergänzt nur, wo natives HTML/CSS nicht ausreicht.
  • Ein Token-System, eine Quelle der Wahrheit. tokens.css/colors.css sind die einzige Werteliste. Alles andere (auch Web Awesome, über die Bridge) übersetzt nur, dupliziert nicht.
  • Kein Build-Schritt. Kein LESS/Sass, kein Bundler. @import + Cascade Layers regeln die Reihenfolge. Web Awesome/Font Awesome sind selbst gehostet (vendor/), keine CDN-Abhängigkeit.
  • Kein Utility-Klassen-Wildwuchs. Kleine, kuratierte Utility-Sets statt einer vollständigen Tailwind-artigen Matrix. Neue Utilities nur, wenn ein echter, wiederkehrender Bedarf entsteht.
  • Solides Grundgerüst, kein Übertreiben. Die Basis (Tokens, Reset, Layout-Primitiven, Kernkomponenten) ist bewusst vollständig und stabil - alles Individuelle kommt als eigene Komponente/Seite hinzu, wenn der Bedarf konkret ist, nicht vorsorglich.
  • Verifiziert, nicht angenommen. Jede nicht-triviale Änderung wird im echten Browser getestet (Playwright), besonders Dark-Mode-Kontrast und Web-Awesome-Interna, die schlecht dokumentiert sind.

Architektur

Ladereihenfolge in ncss.css, per Cascade Layers explizit statt über Spezifität geregelt - eine spätere Layer-Regel gewinnt immer, unabhängig vom Selektor:

  1. wa-native..wa-theme-overrides
  2. tokens
  3. reset
  4. base
  5. helpers
  6. components
  7. webawesome-bridge

Die wa-*-Layer (Web Awesomes eigene) stehen ganz vorne (niedrigste Priorität) - dadurch gewinnt webawesome-bridge.css immer gegen Web Awesomes eigenes Default-Theme, unabhängig von der <link>-Reihenfolge im HTML (Layer-Order ist seitenweit global).

Dateistruktur:

  • tokens.css / colors.css - alle Design-Tokens
  • reset.css - nur Browser-Inkonsistenzen, bleibt "dumm"
  • base.css - neutrale Defaults für nackte HTML-Tags, keine Optik-Meinung
  • helpers/*.css - Utility-Klassen, ein Thema pro Datei
  • components/*.css - ein Baustein pro Datei, opt-in per Klasse
  • webawesome-bridge.css - Web-Awesome-Tokens → ncss-Tokens
  • vendor/ - selbst gehostetes Web Awesome Free + Font Awesome Free

Tokens

Alle Tokens tragen das Präfix --ncss-*. Farb-Skalen (100/300/500/700/900) werden aus EINER Basisfarbe per color-mix() berechnet, nicht von Hand gepflegt - siehe colors.css für die genaue Herleitung (inkl. der light-dark()-Sonderbehandlung für 100/300/700/900).

--ncss-color-bg
--ncss-color-bg-subtle
--ncss-color-surface
--ncss-color-text
--ncss-color-brand
--ncss-color-brand-2
--ncss-color-success
--ncss-color-warning
--ncss-color-danger

Vollständige Skalen (100-900) und alle übrigen Token-Kategorien (Typografie, Abstand, Radius, Schatten, Bewegung, Breakpoint-/Container-Query-Konventionen) live in index.html#farben bzw. direkt in tokens.css/colors.css nachlesen - hier nur ein Überblick.

Icon-System

Eigene SVG-Icons als CSS mask-image (helpers/icons.css) - erben currentColor, skalieren mit font-size, brauchen keinen Markup-Inhalt:

<span class="ncss-icon ncss-icon-close"></span>

Modular per Absicht: Komponenten wie .ncss-dialog-close stylen nur die Fläche (Position/Größe/Form), nicht das Icon selbst. Das Default-Icon lässt sich 1:1 austauschen, z.B. gegen Font Awesome:

<button class="ncss-dialog-close" command="close" commandfor="..." aria-label="Schließen">
  <i class="fa-solid fa-xmark" aria-hidden="true"></i>
</button>

Aktuell enthalten: .ncss-icon-close, .ncss-icon-chevron-down, .ncss-icon-menu, .ncss-icon-play. Weitere nach demselben Muster ergänzen (eigenes SVG als mask-image data-URI) statt vorsorglich ein großes Set anzulegen.

Formular-Erweiterungen (.ncss-switch, .ncss-range) liegen bewusst in helpers/forms.css statt eigener Dateien - sie sind reine Stylings nativer Elemente, keine eigenständigen Bausteine mit Slots/Struktur.

Art Direction & Fokuspunkt

Bilder: <picture> mit mehreren <source media="..."> ist die native, voll unterstützte Lösung für "andere Bilddatei je Viewport" - siehe media.html#art-direction.

Video: <source media="..."> innerhalb <video> wurde aus der Spec/den meisten Browsern entfernt (nur Safari/WebKit unterstützt es noch als Altlast) - kein cross-browser-taugliches Feature (per Recherche geprüft, nicht angenommen). Ohne JS bleibt .ncss-video--responsive-crop (components/video.css) als Annäherung: dasselbe Video, anderer Bildausschnitt per object-fit je Breakpoint. Echtes anderes Filmmaterial je Breakpoint bräuchte kleines JS (matchMedia + src-Wechsel) - bewusst nicht Teil von video.css, um es JS-frei zu halten.

Fokuspunkt: --ncss-focus-point (tokens.css, Default center) steuert object-position überall, wo object-fit: cover genutzt wird (Ratio-Helpers, .ncss-card-media, .ncss-video). Pro Bild/Video überschreibbar: style="--ncss-focus-point: 20% 80%" (dieselbe Custom-Property-Parametrisierung wie --ncss-grid-min).

Web-Awesome-Bridge

webawesome-bridge.css übersetzt Web Awesomes semantische Tokens (--wa-color-{familie}-{fill|border|on}-{quiet|normal|loud}, --wa-font-*, --wa-space-*, --wa-border-radius-*) auf ncss-Tokens - ein Layer auf :root reicht für die meisten Komponenten, kein ::part()-Gefrickel nötig.

Wichtige, per Test gefundene Fallstricke (bevor man die Bridge erweitert, unbedingt lesen):

  • appearance="filled" ist bei <wa-button> die WEICHE Variante (fill-normal), appearance="accent" die KRÄFTIGE (fill-loud) - umgekehrt von dem, was der Name vermuten lässt. Bei Tag/Badge ist die Zuordnung nochmal anders (filled = fill-quiet). Immer im kompilierten Component-Code nachsehen (vendor/webawesome/dist-cdn/chunks/*.js), nicht der Doku vertrauen.
  • -100/-300-Farbstufen MÜSSEN light-dark()-gewrappt sein (mischen im Dark Mode gegen Schwarz statt Weiß), sonst sind z.B. gefüllte Buttons im Dark Mode unlesbar (heller Text auf hellem Chip). Die dazu passende Textfarbe (-on-soft) muss GENAUSO gewrappt sein und selbst zwischen den Modi wechseln, nicht nur die Fläche.
  • Self-Hosting mit relativem Pfad braucht data-webawesome="..." auf dem Loader-<script> - ohne das verdoppelt sich der Basis-Pfad und alle Komponenten-Chunks 404en.
  • Web Awesome ist komplett ES-Module-basiert - funktioniert NICHT über file:// (Browser blockieren type="module"/import() ohne echten Origin). Immer über einen lokalen Server testen.

Konventionen

  • Keine Inline-Styles, wenn vermeidbar - Ausnahme: style="--ncss-grid-min: Xrem" (Parametrisierung einer Custom Property, keine Deko).
  • Seiten-eigenes CSS (Demo-Seiten) lebt in einem eigenen <style>-Block oder einer Datei neben der Seite, demo-*-Präfix, nie in den ncss-Dateien selbst.
  • BEM-Modifier (.ncss-card--horizontal) für STRUKTURELLE Varianten einer Komponente. Rein gestalterische Eigenschaften wie Rahmen/Ecken/Schatten dagegen NICHT als Komponenten-Modifier (z.B. war .ncss-card--elevated nur innerhalb von Cards nutzbar) - dafür die allgemeinen .ncss-border/.ncss-radius-*/.ncss-shadow-*-Utilities (helpers/elevation.css), die auf jedem Element funktionieren.
  • Container-Query-Schwellen und Breakpoints sind dokumentierte feste Werte (siehe tokens.css), keine Custom Properties - var() funktioniert aktuell in keinem Browser innerhalb von @media/@container-Bedingungen.
  • Single-direction Margins (nur margin-block-end) statt Owl-Selector - siehe base.css-Kommentar für den Float-Bug, der zum Wechsel führte.

Erweitern

  1. Neues Token fehlt? In tokens.css/colors.css ergänzen, NICHT den Wert direkt in einer Komponente hart codieren - auch wenn er nur einmal gebraucht wird, sobald ein zweiter Nutzungsort absehbar ist.
  2. Neue Komponente: eigene Datei unter components/, in ncss.css im Layer components importieren, ausschließlich var(--ncss-*) verwenden.
  3. Neues Icon: eigenes SVG als mask-image-Klasse in helpers/icons.css nach demselben Muster wie .ncss-icon-close.
  4. Neue Web-Awesome-Komponente einbinden: zuerst im kompilierten Source nachsehen, welche --wa-color-*-Variablen sie tatsächlich nutzt (Doku ist unzuverlässig), dann in webawesome-bridge.css ergänzen statt eigene Werte zu setzen.
  5. Jede nicht-triviale Änderung mit Playwright in einem echten Browser verifizieren - insbesondere Dark Mode (Kontrast!) und alles, was mit Web Awesome zusammenhängt.
